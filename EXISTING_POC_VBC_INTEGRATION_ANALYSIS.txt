5. EXISTING HEALTHCARE WORKFLOW

Active documentation workflow:
  Streamlit consultation page -> browser audio/local speech recognition or
  transcript entry -> HealthcareApiClient -> POST /encounters/scribe ->
  EncounterAgent/AmbientScribeAgent -> SOAP/EncounterContext -> optional
  POST /encounters/cds -> retrieval/CDS agent -> clinician review/edit ->
  local consultation record saved to clinical_records.json.

Coding and billing workflow:
  Review selected record/transcript -> detected clinical insights -> ICD-10
  and CPT/HCPCS suggestions using local matchers and/or POST /codes -> clinician
  selection/review -> chargemaster line estimates.
  The Codes page creates an estimated bill in Streamlit state. The separate
  IPD Billing page reads IPD workbook encounter/charge lines, validates and
  creates a session bill. Either bill can populate Claim Generation.

Claim workflow:
  Claim Generation selects a generated bill by patient/encounter, checks bill
  arithmetic and supporting documents, gathers patient/provider/payer fields,
  creates a structured claim record, runs claim/document validation, and offers
  JSON/text/837-format outputs. frontend/claim_generator.py formats demo 837P
  or 837I segments. This is a POC artifact, not a verified payer submission or
  a production X12 clearinghouse integration. Generated claim records and
  validation reports are session-scoped, not a durable claims ledger.

6. PATIENT MODEL, IDENTIFIERS, SELECTION, AND SOURCE

There is no canonical ORM Patient model. app/api/schemas.py defines
EhrPatientPayload, a permissive Pydantic payload with optional patient_id, MRN,
demographic/contact fields and a free-form payload dictionary. The active EHR
service stores workbook-shaped dictionaries.

The active EHR source is
Epic_Inspired_USA_50_Patient_Demo_Athena_Care_Gap.json, created from
Epic_Inspired_USA_50_Patient_Demo.xlsx by app/services/ehr_json_service.py.
Patient_Master uses Patient_ID and MRN columns. Existing Patient_ID values in
this source follow a P-plus-digits form; new JSON-store patients use P plus a
six-digit sequence. The secondary, currently unrouted SQLite service can mint
PT-prefixed random IDs when a source identifier is missing. Do not mix these
ID schemes.

The EHR Demo Data selectbox widget key is ehr_patient_selection. It stores the
visible patient label; the selected patient ID is derived locally from the
label-to-ID mapping and is not a shared canonical session key. No common
selected_patient_id key connects all pages. Claim Generation uses its own
claim_generation_patient widget and generated-bill state. Consultation records
may contain ehr_patient_id, but a record's own id is also used as fallback in
some code. No identifier crosswalk was found.

7. ENCOUNTER MODEL AND DATA

app/models/encounter.py defines EncounterContext, not a persisted EHR
Encounter entity. Fields are transcript, soap_note, patient_summary,
retrieved_guidelines, recommendations, and metadata. Encounter API request and
response models inherit/use this context.

The workbook-shaped Encounters records carry Encounter_ID, Patient_ID, Date,
Type, Department, Provider, Facility, Status, Primary_Diagnosis_Code,
Primary_Diagnosis, Priority, and Disposition_or_Follow_Up. Related sheet
records include Problems (ICD-10-CM, clinical/verification status, onset and
resolved dates), Orders_Procedures (order/encounter IDs, CPT/HCPCS,
description/status), Vitals, Labs, and Clinical_Notes. These are dictionary
rows; there are no typed Observation, Condition, Procedure, or Claim models.
The source encounter IDs are preserved as supplied; no single normalized
encounter_id format is enforced throughout the application.

The separate IPD Billing workbook has admission/discharge date/time, ward,
room/bed, length of stay, diagnoses, and charge lines. That is distinct from
the standard JSON EHR Encounters row. Clinical consultation records have their
own local id and date/time fields and only link to EHR encounters when
ehr_encounter_id is supplied.

8. BP, HbA1c, LABS, ADMISSIONS, DISCHARGES, SCREENINGS, HISTORICAL VISITS

The EHR JSON workbook has structured Vitals columns for systolic/diastolic BP
and other vital signs, and Labs columns for result date, LOINC, test name,
result, unit, reference range, flag/status, lab, and ordering provider.
app/rules/rule_engine.py can regex-extract HbA1c and BP only from a text patient
summary. It flags HbA1c >9 and BP >140/90; it also detects chest-pain language,
retinal-screening-gap phrases, and allergy phrases. Search shows this rule
engine is not wired into the active encounter/CDS route, so these checks are
not current automated EHR measure evaluation.

Admission/discharge data is present in the IPD Billing workbook and can appear
in claim records/837I output. The standard Encounter row does not provide a
uniform, explicit admission/discharge event model. No dedicated discharge
event or readmission model was found.

The EHR has Immunizations and Appointments sheets, but no standardized
screening-eligibility service. Retinal-screening detection exists only as a
phrase rule. VBC sample measure outputs include BP Control, Breast Cancer
Screening, Colorectal Screening, and Glycemic Assessment. The sample output
rows do not themselves define eligibility/denominator logic.

Historical visits can be read from the Encounters sheet/chart API and from
clinical_records.json consultation records. Dates are represented differently
across surfaces (workbook source dates, ISO serialization, and frontend
dd/mm/YYYY consultation strings). Normalize timezone/date semantics before
combining or calculating lookback windows. No unified timeline API was found.

9. CLAIM, DOCUMENT, PROVIDER, AND FACILITY STRUCTURES

EHR source claim rows are in Billing_Claims, with claim/patient/encounter IDs,
service date, CPT/HCPCS, description, units, charge/payment/balance, payer,
status, and currency fields. The JSON EHR bill path creates Generated_Bills
and Generated_Bill_Lines sheets, and may append draft line entries to
Billing_Claims. The active Streamlit Claim Generation claim is a dictionary
with Claim ID, Encounter ID/Type, Claim Type/Generated Format, Status,
Claim Amount, Patient Information, Provider Information, codes, Charges,
Supporting Documents Validation, plus professional (837P) or facility (837I)
fields. IPD facility fields include admission/discharge dates, revenue codes,
bill type, and facility charges. EHR bills and Streamlit claims are different
structures and persistence paths.

Provider data is represented in patient/encounter workbook rows, Care_Team,
claim provider dictionaries (Name/NPI), and the VBC providers.csv (provider_id,
provider_name, specialty, npi). Facility data is a string or facility object
with name/ID; the claim page has demo fallback values. No single Provider or
Facility model/service exists.

Supporting documents are discovered from
data/supporting_documents/ folders (SOAP Notes, CT Scan Reports, X-Ray Reports,
Lab Reports, Procedure Notes), data/supporting_documents.json, and approved
SOAP-note JSON files. Repository records use document IDs/type/path and
patient/encounter scope where available. Claim validation maps CPTs to required
document types and checks available files/record/session content; this is not
a complete document management or clinical evidence repository.

11. CURRENT STORAGE

  CSV: VBC CSV files are inside data/synthetic_vbc_dataset.zip; no active VBC
    loader/writer was found. The existing application does not write VBC CSVs.
  JSON: active EHR store is
    Epic_Inspired_USA_50_Patient_Demo_Athena_Care_Gap.json, initialized from
    the EHR workbook and rewritten by EHR API mutations. Streamlit consultation
    records use Clinical_decision_support/clinical_records.json. Other JSON
    includes coding/reference data, supporting-document metadata, approved
    SOAP notes, and the two VBC JSON samples in the archive.
  SQLite: app/services/ehr_demo_service.py defines patients,
    patient_records, and bills in data/nuucare_ehr_demo.db; the file is present
    in this working tree, but API routes use ehr_json_service.py instead.
    Chroma's generated local SQLite database stores retrieval data, not EHR.
  Excel: workbook-shaped EHR source, IPD billing data, chargemaster, and legacy
    code/billing demo workbooks.
  File system: supporting documents, approved SOAP JSON, Word knowledge base,
    and generated RAG/index artifacts.
  In-memory: Streamlit session state stores current consultation state,
    estimated/IPD bills, claim-generation bills, claims, and validation
    reports. It is not durable across session loss.

EHR JSON updates use a process-local lock and atomic temporary-file replacement.
This does not coordinate concurrent processes. clinical_records.json uses a
fixed .tmp sibling and has no visible inter-process lock. Do not add parallel
CSV writers without a single-writer or transaction strategy.

Compatibility check (identifiers only; no values emitted): the VBC archive has
20 unique patient IDs and 94 unique encounter IDs; its encounter patient
references resolve within its own patient list. There are zero exact patient
ID matches and zero exact encounter ID matches against the current
workbook-backed EHR source. Current EHR Patient_ID values use a different
P-plus-digits form. No common crosswalk, FHIR mapping, or documented identity
matching rule was found. Do not match by name/DOB or fuzzy demographics; use an
approved explicit crosswalk or keep VBC identities isolated.

field names are conceptually mappable to the EHR's workbook sheets, but code
systems, status vocabulary, date semantics, provider IDs, measure definitions,
and identity keys need mapping/validation. The VBC records are not directly
loadable by the active EHR JSON service without transformations; no migration
or import should occur in read-only phases.

17. SAFE READ-ONLY INTEGRATION POINTS

Existing GET-only interfaces suitable for reading current EHR data:
  HealthcareApiClient.list_patients() -> GET /patients
  HealthcareApiClient.get_patient_chart(patient_id) ->
    GET /patients/{patient_id}/chart
  HealthcareApiClient.list_patient_records(patient_id, record_type) ->
    GET /ehr/patients/{patient_id}/records
  HealthcareApiClient.list_bills(patient_id) -> GET /ehr/bills
  HealthcareApiClient.export_patient_data(patient_id) ->
    GET /patients/export or GET /ehr/export

These reads expose workbook-shaped rows; inspect Patient_ID/Encounter_ID and
filter client-side by exact ID where required. `get_patient_chart` groups
associated sheets by Patient_ID. Use these only for exact linked entities.
Do not call POST/PUT/DELETE endpoints from a read-only VBC view. There is no
read-only document API; use the current supporting-document repository helper
with its path constraints and treat document contents as sensitive.

Current encounter records, diagnoses, procedures, claims, and observations can
be read from chart/records endpoints or export when the EHR ID is already
verified. The session-only ambient encounter record is not automatically an
EHR encounter; no current encounter synchronization is safe until identity and
encounter linkage are explicit. Existing codes/claims should remain read-only
evidence until a reviewed mapping defines their meaning.

18. INTEGRATION RISKS

  Patient-ID mismatch: verified zero exact ID overlap; implicit joining would
    attribute clinical information to the wrong person.
  Encounter-ID mismatch: verified zero exact encounter overlap; no common ID
    contract or crosswalk.
  Duplicate data: CSV records duplicate facts available in workbook sheets;
    importing would create competing diagnoses, observations, claims, and
    timelines.
  Date/unit/code mismatch: mixed date formats, observation vocabularies,
    normalized units, ICD/CPT/HCPCS meanings, status and verification values.
  Static outputs: measure_results, care_gaps, risk_scores, and population
    summary are supplied result snapshots without complete calculation rules.
  Hardcoded paths: EHR workbook/JSON paths are project-relative constants;
    chargemaster supports CHARGEMASTER_PATH and fallback paths; other workflows
    also refer to named project workbooks. Keep path resolution anchored to
    project root and do not assume current working directory.
  Session coupling: generated claims and bills live in Streamlit state; UI
    state is not a durable source of truth and differs across pages.
  CSV writes: do not edit CSV members in place or write concurrent CSV results.
    The current JSON locking is process-local and does not protect multi-process
    writers.
  Privacy: archive fields include direct identifiers/contact fields; even
    files labeled synthetic should be handled as sensitive until verified.
  Clinical/coding risk: code suggestions, demo chargemaster rates, and generic
    text rules are not validated measure logic, clinical advice, or claim
    approval.
  Deployment boundary: FastAPI binds 0.0.0.0:8000 and no auth controls were
    found. Keep the POC local/restricted; do not expose new patient endpoints
    publicly.
  Audit gap: current transcript display and static VBC audit CSV do not make
    an immutable production audit system.

19. PHASED INTEGRATION PLAN

Phase 1 - Read-only VBC:
  Read archive members in memory, validate required headers/internal
  references, render a separate VBC Patient 360/population view, and keep VBC
  IDs separate from EHR IDs. No EHR writes, claim writes, CSV changes, or
  demographic matching. Display source/as-of/provenance and synthetic-data
  notice.

Phase 2 - Dynamic measure evaluation:
  Obtain approved specifications for M-BP, M-BCS, M-COL, and M-GA. Define
  denominator, exclusions, evidence types, lookback, date handling, units,
  status, threshold, and expected outcomes. Implement pure deterministic
  functions with tested fixtures; compare to supplied results as a QA signal,
  not as truth. Version the logic and explain each state.

Phase 3 - Workflow and gap closure:
  Create explainable care gaps, plans, outreach records, and audit events in an
  explicitly isolated POC store. Use review/confirmation for status changes.
  Do not send messages or alter EHR/claims in this phase.

Phase 4 - Current encounter synchronization:
  Only after a signed-off exact patient/encounter crosswalk and event/consent
  rules exist, expose read-only encounter evidence and define a tested
  synchronization boundary. Add narrowly scoped APIs only if required.
  Preserve source IDs and reconciliation provenance; never merge by names.

Phase 5 - Optional AI summaries:
  Add optional summarization only after deterministic results are stable.
  Send minimum necessary data under approved privacy controls, cite source
  evidence, label generated text, and keep AI output out of measure state,
  scoring, coding, and durable records unless separately reviewed.
